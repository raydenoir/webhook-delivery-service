# Webhook Service

HTTP API для регистрации получателей webhook и приема событий.
Сервис хранит подписки, события и доставки в PostgreSQL, проверяет адреса получателей
и защищает API ключом доступа.

## Локальный запуск

Требуется Docker Compose. Команды выполняются из корня проекта.

```powershell
Copy-Item .env.example .env
docker compose up -d --build --wait
```

Compose запускает API, диспетчер, Celery, PostgreSQL и RabbitMQ.
Миграции применяются до запуска приложения. API доступен на порту 8000.

## Документация API

- [Swagger UI](http://127.0.0.1:8000/docs) - описание маршрутов и отправка запросов.
- [ReDoc](http://127.0.0.1:8000/redoc) - справочник API.
- [OpenAPI JSON](http://127.0.0.1:8000/openapi.json) - схема API.

Примеры тел запросов, ограничения полей, заголовки и коды ответов доступны
в документации API. Кнопка Authorize в Swagger UI принимает значение `API_KEY`.

## Настройки

Настройки задаются в `.env` или в окружении процесса. Переменные окружения
имеют приоритет. Значения в `.env.example` предназначены для локального запуска.
Compose задает адреса PostgreSQL и RabbitMQ через имена сервисов.

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `API_KEY` | Ключ доступа к подпискам, событиям и доставкам |
| `BROKER_URL` | Подключение к RabbitMQ |
| `ALLOWED_WEBHOOK_HOSTS` | JSON-массив разрешенных хостов получателей |

PostgreSQL 17 запускается через Compose и хранит данные в Docker volume.
Команда `docker compose stop` останавливает БД с сохранением данных.

## Прием событий

HTTP 202 подтверждает сохранение события и доставок для активных подходящих
подписок в одной транзакции. Повтор запроса с тем же ключом
идемпотентности и содержимым возвращает прежнее событие. Тот же ключ с другим
содержимым приводит к HTTP 409.

## Отправка webhook

Диспетчер выбирает готовые доставки из PostgreSQL и передает их UUID в RabbitMQ.
Celery выполняет HTTP-попытки.

[Пример запросов](examples/requests.http) показывает создание подписки с секретом,
прием события, просмотр попыток и ручной повтор. Получатель проверяет
`X-Webhook-Signature` по исходным байтам тела, как описано в документации API.

Флаг `--once` у диспетчера ограничивает запуск одним проходом до 100 заданий.
Состояния, история и расписание повторов хранятся в PostgreSQL.
После сбоя публикации диспетчер повторяет ее через 30 секунд.
Просроченные HTTP-попытки восстанавливаются автоматически в пределах лимита.
Получателю следует учитывать `X-Webhook-Id`, поскольку возможна повторная доставка.

## Проверки

Для локальных проверок требуются Python 3.13 и uv.
Workflow Checks запускает проверки и тесты на Linux при push и pull request.

```powershell
uv venv --python 3.13
uv sync --locked
uv run ruff check .
uv run ruff format --check .
docker compose --profile test up -d --wait postgres-test rabbitmq-test
uv run pytest
```

Тестовый PostgreSQL работает на порту 5433 и хранит данные во временной памяти.
Pytest применяет миграции и очищает таблицы перед каждым тестом и после него.
Обычная БД сервиса не используется, настройки из `.env` для тестов не требуются.

Для другого тестового сервера доступна переменная `TEST_DATABASE_URL`.
Имя базы должно быть `webhook_test`, ее данные удаляются при запуске тестов.
Одновременный запуск нескольких прогонов на одной тестовой БД не поддерживается.

Тесты настоящего Celery worker включаются на Linux командой
`RUN_INTEGRATION_TESTS=1 uv run pytest`. Для них используется отдельный RabbitMQ
на порту 5673 или `TEST_BROKER_URL` с vhost `webhook_test`.
HTTP-получатель в этих тестах имитируется.
